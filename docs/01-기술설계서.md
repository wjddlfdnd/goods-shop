### 렌더링·캐시 원칙
- Next.js 16 `cacheComponents` 사용. 재고·판매 상태·장바구니·주문은 **요청 시점 데이터**로 다룬다: 조회 함수 앞에 `await connection()`, 화면은 `<Suspense>`로 감싼다.
- 카테고리처럼 거의 안 바뀌는 데이터만 필요하면 `'use cache'` + `cacheTag`, 관리자 수정 시 `revalidateTag`(8단계).
- `params`·`searchParams`·`cookies()`는 비동기 API(await).

## 3. 인증·권한 (U-01·U-02·A-01, PRD 7.1)

- 가입: 이메일 고유, 비밀번호 8자 이상 → bcrypt(cost 10) 해시. 연락처는 입력 중 하이픈 자동, 저장은 숫자 10–11자리(v1.4, DB CHECK).
- 로그인: 무작위 32바이트 토큰 → 쿠키 `gs_session`(httpOnly, SameSite=Lax, Secure(배포), 14일). DB `Session.id`에는 토큰의 SHA-256만 저장.
- 권한: 서버에서 매 요청 세션 → 사용자·역할 확인. 회원 전용 API는 401, 관리자 API는 회원·비회원 모두 403.
- 관리자 화면 접근 거부(v1.3): `src/proxy.ts`(구 middleware)에서 `/admin/**` 요청의 세션 쿠키를 확인하고, 관리자 레이아웃에서 역할을 다시 검사한다. 거부 시 `/?notice=admin-only`로 이동 → 홈에서 "관리자만 들어갈 수 있는 페이지입니다" Notice(live). 비회원도 같다.
- 로그인 후 원래 행동 복귀(U-02): 로그인 화면에 `next`(원래 경로)와 `intent`(cart/buy + 옵션·수량)를 넘기고, 로그인 성공 후 서버가 의도를 실행한 뒤 이동한다. 실행 시점에 품절이면 상세로 돌려 품절 안내(PRD 4.2).

## 4. 핵심 트랜잭션 (PRD 6장)

### 4.1 모의 결제(O-05)
주문서 진입 시 `idempotencyKey`(UUID)를 발급해 폼에 숨겨 둔다. 결제 요청은 하나의 DB 트랜잭션:
1. 같은 `idempotencyKey` 주문이 있으면 그 주문을 그대로 돌려준다(중복 클릭·새로고침).
2. 주문 항목마다 조건부 차감: `UPDATE "ProductOption" SET stock = stock - $q WHERE id = $id AND stock >= $q` — 갱신 0행이면 재고 부족으로 전체 롤백(409 `OUT_OF_STOCK`, 남은 수량 포함). CHECK(stock ≥ 0)가 이중 안전장치.
3. 판매 중지 상품이 섞였으면 롤백(409 `UNAVAILABLE`).
4. 주문 번호 `YYYYMMDD-6자리 난수`(D-7) 생성, 고유 충돌 시 재시도(최대 3회).
5. `Order`·`OrderItem`(상품명·옵션명·단가 복사) 생성, 상태 `PAID`.
6. 장바구니 경유면 주문된 `CartItem` 삭제(가정, 7.3).
실패 시 아무것도 바뀌지 않고 화면은 입력값을 유지한 채 "결제 다시 시도"(M-Order--error). 동시 결제 재고 초과 0건은 9단계 M5로 검증.

### 4.2 카테고리 삭제(A-05, D-12)
트랜잭션: 판매 중 연결 상품 수 확인(>0이면 409 `HAS_ON_SALE`) → 판매 중지 연결 상품을 미분류로 이동 → 카테고리 삭제. 미분류(`isSystem`)는 수정·삭제 불가(403).

### 4.3 주문 취소(2차, O-07)
`UPDATE "Order" SET status='CANCELED' WHERE id=$id AND status='PAID'` 조건부 갱신 → 0행이면 409 → 주문 상품 수량만큼 재고 복구. 한 트랜잭션.

## 5. 규칙을 지키는 위치

| 규칙 | DB | 서버 | 화면 |
|---|---|---|---|
| 재고 0 미만 금지 | CHECK | 조건부 갱신 | 수량 상한(재고) |
| 수량 ≥ 1, 재고 이하(7.3) | CHECK(≥1) | zod + 재고 비교 | QuantityStepper min/max, 초과 시 안내 |
| 같은 옵션 재담기 합산(D-5) | UNIQUE(userId, optionId) | upsert + 합산 후 재고 비교 | — |
| 기본 배송지 1개(U-04) | 부분 고유 인덱스 | 새 기본 지정 시 이전 해제(트랜잭션) | — |
| 미분류 1개·노출 금지(D-12) | 부분 고유 인덱스 | 사용자 조회에서 제외, 등록·수정 선택지 제외 | — |
| 주문 상태 순서(A-07, 2차) | — | 다음 단계 1개만 허용 | 선택지 1개 |
| 연락처 숫자만(v1.4) | CHECK | 하이픈 제거 후 검증 | 입력 중 하이픈 자동 |
| 금액 계산(7.4) | 정수(원) | 서버에서 다시 계산(클라이언트 금액 불신) | 표시만 |

## 6. 이미지 (A-03)
- 개발: `public/uploads/`(Git 제외). 배포: Vercel Blob(가정). DB에는 URL만.
- 대표 1장 + 상세 여러 장, 개수·용량 제한: 이미지 10장, 장당 5MB, jpg/png/webp(가정 — PRD 10.5의 7단계 결정 항목).
- 업로드 실패 시 입력값 유지 + 오류(D-AdminProducts--error).

## 7. 오류 응답 형식
`{ "error": "CODE", "message": "사용자에게 보여 줄 문장" }` + HTTP 상태(400 입력, 401 로그인 필요, 403 권한, 404 없음, 409 상태 충돌·재고, 500 서버). 화면 문구는 DESIGN 4.1의 상태 화면 문구를 그대로 쓴다.

## 8. 배포·운영(가정, 10단계 확정)
- Vercel(앱) + Neon(PostgreSQL, 풀링 URL) + Vercel Blob. 환경 변수: `DATABASE_URL`, `SESSION_SECRET`, `BLOB_READ_WRITE_TOKEN`.
- 배포 시 `prisma migrate deploy`. 롤백은 Vercel 이전 배포 + 마이그레이션은 앞으로만(되돌릴 때는 새 마이그레이션).
- 배포 환경은 테스트 데이터만(PRD 6장 개인정보).

## 9. 7단계 결정·가정 목록
- 결정(사용자): 스택 Next.js + TypeScript, PostgreSQL + Prisma, 문서는 저장소 `docs/`.
- 가정(LEDGER 기록): 세션 직접 구현, 이미지 10장·5MB, 배포 Vercel + Neon + Blob, 인기순은 8단계 집계 전까지 최신순 대체.
