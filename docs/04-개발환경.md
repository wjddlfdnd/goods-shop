# 개발 환경 (7단계)

> 원본은 Notion "굿즈 쇼핑몰 > 06. 기술 설계"(API는 "03. API 명세서", ERD 그림은 ERDCloud)다. 이 파일은 사본이며, 내용이 다르면 Notion을 따른다.


## 필요한 것
- Node.js 22 이상, npm 10
- PostgreSQL 16 — Docker가 있으면 `docker compose up -d db`, 없으면 직접 설치

## 처음 실행
```bash
cp .env.example .env          # DATABASE_URL, SESSION_SECRET 확인
docker compose up -d db        # 또는 로컬 PostgreSQL에 goodsshop DB 생성
npm install
npm run db:setup               # 마이그레이션 + 시드
npm run dev                    # http://localhost:3000
npm run smoke                  # 서버가 뜬 상태에서 기본 데이터 조회 확인
```

## 스크립트
| 명령 | 하는 일 |
|---|---|
| `npm run dev` | 개발 서버 |
| `npm run build` / `npm start` | 운영 빌드·실행 |
| `npm run db:migrate` | 개발 마이그레이션 생성·적용(`prisma migrate dev`) |
| `npm run db:seed` | 시드 데이터 다시 넣기(개발 DB를 비우고 채움) |
| `npm run db:setup` | 마이그레이션 적용 + 시드 |
| `npm run db:studio` | Prisma Studio(데이터 보기) |
| `npm run smoke` | `/api/health`·`/api/categories`·`/api/products`를 호출해 7단계 완료 기준 확인 |
| `npm run design:qa` | 디자인 캔버스 자동 QA(`design/qa`) |

## Git 브랜치 전략 — Git Flow (2026-11-26 사용자 결정)
참고: [Git branch 전략](https://velog.io/@kw2577/Git-branch-%EC%A0%84%EB%9E%B5), [우아한형제들 — 우린 Git-flow를 사용하고 있어요](https://techblog.woowahan.com/2553/)

| 브랜치 | 만드는 곳 → 병합하는 곳 | 용도 |
|---|---|---|
| `main` | — | 배포 브랜치(글의 `master` 역할). 직접 커밋하지 않는다 |
| `develop` | `main`에서 한 번 분기 | 개발 기준 브랜치. 기능을 모으는 곳 |
| `feature-<기능>` | `develop` → `develop` | 기능 단위 개발. 예: `feature-auth`, `feature-cart` |
| `release-<버전>` | `develop` → `main`·`develop` | 배포 전 QA(9단계). QA 중 버그는 이 브랜치에 바로 고친다. 예: `release-1.0.0` |
| `hotfix-<버전>` | `main` → `main`·`develop` | 배포 후 긴급 수정. 예: `hotfix-1.0.1` |

- 병합은 항상 `--no-ff`(GitHub PR은 "Create a merge commit")로 해서 브랜치 기록을 남긴다. squash·rebase 병합은 쓰지 않는다.
- feature 브랜치는 GitHub에 push하고 `develop` 대상 PR을 열어 병합한다. PR 본문에 기능 ID(PRD 5장)와 확인 결과를 적는다.
- `release`를 `main`에 병합하면 태그 `v<버전>`을 단다(가정).
- 커밋 메시지: `feat: 장바구니 담기 API` 처럼 종류 + 한국어 요약.
- `.env`, `src/generated/`, `public/uploads/`는 커밋하지 않는다.
